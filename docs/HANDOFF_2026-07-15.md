## The camera: what to know before touching it

**Current architecture** (`GRAD_ArsenalMenu.c`):
- Isolated world via `BaseWorld.CreateWorld("InspectionPreview", "InspectionPreview")`, hold the
  `SharedItemRef` (that ref is what keeps the world alive), camera **slot 0** (free in an isolated
  world), vanilla studio-set prefab `{4391FE7994EE6FE2}worlds/Sandbox/InventoryPreviewWorld10.et`
  (`IsValid()`-guarded), `m_wPreview.SetWorld(m_PreviewWorld, 0)`.
- **Two entities, two jobs**: `m_PreviewCharacter` = real mutable clone in the **LIVE** world (its
  inventory only works there), never rendered. `m_PreviewVisual` = visual-only clone in the isolated
  world via `InventoryItemComponent.CreatePreviewEntity(world, camera)` on the clone's own item
  component; this is what renders, and what `PositionCamera` frames. Rebuilt every mutation.

**Two engine facts, both live-proven the hard way — do not re-litigate:**
- A fresh `BaseWorld.CreateWorld` world has **no game systems**. A mutable entity in it has a
  non-functional inventory: `TrySpawnPrefabToStorage` silently no-ops (8 of 30 items, zero failures
  logged), `Capture` then reads `0 occupied` on all five roots, Confirm refuses "empty loadout".
- `SetCameraEx` does **not** durably retain a one-shot write — re-push it every frame from
  `OnMenuUpdate`. Vanilla's `UpdateView` does exactly this; it is not incidental to its orbit animation.

**Dead ends, all live-tested — do not retry:** driving a camera slot in the LIVE world with a spawned
`SCR_PIPCamera`, in any parenting variant (unparented → renders nothing; parented to character → ~1km
away underwater; parented to a boneless anchor → *identical* to the character-parent result, which is
what disproved the bone-pivot theory). Diagnostics eventually proved `SetWorldTransform` never committed
on that camera in *any* variant — parenting was never the real variable.

## Read this: how I misled this investigation

The camera cost several sessions, and the pattern was consistent enough to be worth naming.

- **I verified fragments, then extrapolated architectures and stated them with more confidence than the
  evidence supported.** I confirmed vanilla's `SCR_InventoryInspectionUI.CreatePreview()` (which previews
  a single static ITEM), then asserted "vanilla never puts a live entity in a preview world" and "this is
  the split vanilla does" as findings. They were extrapolations. The user caught it.
- **I treated "the signature exists" as "this is the right call."** `SCR_CharacterInventoryStorageComponent
  .CreatePreviewEntity` exists and sounded character-shaped, so I used it. The working reference uses the
  plain `InventoryItemComponent` overload. Now corrected, with a warning at the call site.
- **Identical results across attempts were the signal I kept missing.** When the boneless-anchor attempt
  produced *exactly* the same symptom as the character-parent attempt, that meant the variable I was
  changing wasn't the cause. Three parenting variants died before a read-back diagnostic found the truth
  in one test.

**The lesson that actually generalises**: when a change produces the SAME symptom (not merely "still
broken"), stop varying that axis and add a diagnostic that reads back actual state. And check whether a
shipped screen already does the exact thing you're building — the isolated-world answer existed the whole
time.

The engine facts in this doc are safe: each is backed by a specific live log line, not by reasoning.
Anything framed as architecture or intent, verify before trusting.

## Strong lead, not pursued: `SCR_PlayerArsenalLoadout`

`ApplyLoadoutString(IEntity, BaseSerializationLoadContext)` / `ReadLoadoutString(...)` — vanilla's own
full-loadout serialise/apply, almost certainly what the arsenal terminal uses to swap a whole kit. Its
`ApplyEntityStorageString` reportedly removes entities whose slots aren't in the loadout data — i.e. it
REPLACES, which is exactly the pain point behind the `TryEquipReplace` mess. Could replace most of the
hand-rolled `GRAD_LoadoutApply`/`GRAD_LoadoutCapture` walk/spawn/equip logic. Unverified whether its
format suits in-place live editing vs. spawn-time faction loadouts. Architectural — own session.
