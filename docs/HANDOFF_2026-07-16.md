## State in one line

The center preview pane **now renders the character correctly** (confirmed live by the user) after a
long investigation found the real root cause: the camera's position in the isolated preview world is not
controllable from script — only its rotation is. The fix moves the **subject**, not the camera. One new,
higher-priority bug surfaced immediately after: **re-equipping a garment (uniform/vest/trousers) after
removing it reports success in the log but the item never becomes visible — not in the preview, and not
on the real character after Confirm either.** A diagnostic for that is in place; needs one more live test
before a fix.

## Camera: what to know before touching it again

**Root cause, conclusively live-diagnosed via a per-frame orbit test:** `BaseWorld.SetCameraEx`'s
**rotation** columns are honored — a continuously-changing rotation visibly swept the rendered view — but
its **position** column is not: the camera's position never moved relative to the subject no matter what
was written (tested from 0.8m to 10m, including straight up/down). Something else — almost certainly
native machinery inside `InventoryItemComponent.CreatePreviewEntity`/the preview camera slot itself —
pins the camera's position near wherever the subject is. This is NOT documented anywhere (native
`proto external`, no script source) and was found by direct experiment, not reasoning.

**The fix (`GRAD_ArsenalMenu.c`):** since the camera can't be moved, the **subject** is moved instead.
- `RebuildPreviewVisual()`: after `CreatePreviewEntity`, the resulting `m_PreviewVisual` gets an explicit
  `SetWorldTransform` to `PREVIEW_SUBJECT_OFFSET` (currently `"0 -0.8 3"`) with a hand-built 180°-yawed
  rotation matrix (`right=<-1,0,0>`, `up=<0,1,0>`, `forward=<0,0,-1>`) so it faces back toward the camera
  — live-confirmed necessary; the entity otherwise faced away.
- `PositionCamera()`: `camPos` is now **symbolic** (kept non-degenerate but not a real lever) — the only
  thing that matters is `lookTarget`, which now points at `PREVIEW_SUBJECT_OFFSET` instead of a hardcoded
  world point, so the camera's (fixed, engine-owned) position still ends up facing the subject via
  rotation.
- Also fixed along the way, all real and still correct: `GetBounds` → `GetWorldBounds` (local vs. world
  space — `GetBounds` was silently wrong for anything not sitting at world origin), an early `SetWorld`
  bind before the subject exists (was previously bound last), a placeholder `SetCameraEx` write in
  `CreatePreviewWorld()` so the slot is never read in a literally-unwritten state, an explicit
  `previewVisualGe.Update()` call after `CreatePreviewEntity` (same "must force a commit" pattern this
  file already needed once for the item grid), and `SetFixedLOD(0)`/`SetVComponentFlags` on the preview
  entity (found via a genuine line-by-line diff against a reference implementation's `SetEntityQuality()`
  — this project had never called either).
- Also fixed: `m_wPreview.Update()` (the `RenderTargetWidget` itself, not just the world's camera slot) is
  now called after every `SetCameraEx` write, both in `PositionCamera()` and the per-frame push in
  `OnMenuUpdate()` — the pane looked frozen/static across an entire menu session otherwise.

**Tuning still open, not blocking:** `PREVIEW_SUBJECT_OFFSET`'s exact numbers (`0 -0.8 3`) were tuned from
one live screenshot each for rotation and height — good enough per the user ("consider this part done"),
but if a future session wants pixel-perfect centering, this is the constant to adjust, and
`distanceMul`/`eyeHeightFrac` in `PositionCamera` no longer do much (see above) — don't waste time on them.

**A costly mid-session mistake, worth naming so it isn't repeated:** a diagnostic swap
(`DIAG_USE_SIMPLE_ITEM` in `RebuildPreviewVisual`, added to render a simple M9 handgun instead of the
character to isolate a "character-specific vs. pipeline-wide" question) was left **accidentally active**
across several subsequent tests. Every "distance doesn't matter" observation during that window was
silently re-testing the M9, not the character — caught only because `PreviewVisualBoundsDiag` logged an
**identical bounding box across three different character prefabs**, which is the tell for "the render
source never actually changed." Both `DIAG_USE_SIMPLE_ITEM` and `DIAG_SMALL_ITEM_POSE` are now reverted to
`false` and left in the file (harmless, useful for future isolation tests) — check they're still `false`
before trusting any "the subject didn't change" observation.

**Also fixed in the same investigation:** `RebuildPreviewVisual` was still rendering
`m_Context.GetPrimaryTarget()` (the REAL, unedited target) — a leftover from the very first "Step 1"
experiment at the start of this whole camera investigation (isolating whether `CreatePreviewEntity` could
render a dressed character at all, done *before* the camera-position bug was found). This meant the
preview pane never reflected live edits the whole session — confirmed by the user removing a uniform on
the clone and the preview still showing it worn. Now renders `m_PreviewCharacter` (the actual edited
clone) again, matching pre-experiment behavior, with the camera fix layered on top.

## New, higher-priority bug: garment re-equip-after-strip is invisible

**Reproduction:** open the arsenal, click REMOVE on Uniform/Vest/Trousers (or Headgear), then double-click
a catalog item to re-equip that slot. Log reports `Apply: spawned 1 items, skipped 0` (success) every
time. The item does **not** visually reappear — confirmed by the user on both the **preview** and the
**real character after Confirm** (so this is not a stale-preview-render issue; the underlying apply is
genuinely not landing the item on-body).

**Where this lives:** `GRAD_LoadoutApply.c`, `TryEquipReplace()` — the fallback path used whenever there's
no matched captured storage (a plain click-to-equip with no destination chosen), which is exactly the
re-equip-after-REMOVE case. It spawns a bare replacement entity at **world origin with an identity
transform** (`Math3D.MatrixIdentity4(params.Transform)`, no attempt to position it near the character),
then calls `SCR_InventoryStorageManagerComponent.EquipAny(charStorage, spawned, -1)`. `EquipAny` reports
`true`, and the caller trusts that as "done."

**Two live theories, unconfirmed, a diagnostic is already in place for both:**
1. The spawned entity never gets fully attached to a render/skeleton slot and stays a disconnected entity
   sitting at world origin — the manager's bookkeeping says "equipped" without a real visual/positional
   attach.
2. The user's own theory, also plausible: a garment that itself HAS storage (trousers/uniform pockets,
   vest pouches) might be getting nested *inside* another container instead of equipped to the body slot,
   since it superficially "looks like a container" to whatever heuristic `EquipAny`/the manager uses.

**UPDATE (later same day, live-tested): theory 1 confirmed, fix applied.** The diagnostic ran live. Two
data points:
- Re-equipping a BDU Blouse / re-equipping Pilot Coveralls into an already-EMPTY uniform slot: `parent=1`,
  real non-origin `worldPos` — genuinely attached, works fine.
- Re-equipping BDU Trousers right after a one-piece coverall (Suit_Pilot_US_01 / Suit_Tanker_US_01, which
  occupies BOTH the uniform and LEGS slots) was removed from that same LEGS slot: `EquipAny` returned
  `true` but `parent=0` (null) and `worldPos=<0,0,0>` — the spawned entity is a disconnected orphan.
  Confirmed theory 1, not theory 2 (nothing suggests container-nesting here).

**Root cause investigated via arexplorer's real `EquipAny` body** (verbatim, not paraphrased — see
`GRAD_LoadoutApply.c`'s updated comment in `TryEquipReplace`). For our call (`spawned` is a fresh
ground-spawned entity, `sourceSlot` is always null), `EquipAny` takes the synchronous
"picking up item from ground" branch — `TryInsertItemInStorage` if the target slot is empty,
`TryReplaceItem` if occupied — NOT the async `DropAndMoveOperationCallback` path (that one only triggers
when the item's source is an arsenal/dead body/campaign armory, which never applies here). So the async
theory is **ruled out**; the exact mechanism inside `TryReplaceItem`'s native worker
(`ScriptedInventoryStorageManagerComponent`, no script source, same wall as other native calls this
project has hit) is still unconfirmed. Likely candidate, NOT yet live-verified: a one-piece coverall may
not register a persistent, independent LEGS `ClothNodeStorageComponent` slot the way separate trousers do
— it might only be a synthetic/fallback slot on the base character mesh — so after the coverall's removal,
`FindSuitableSlotForItem` for LEGS finds *something* that reports occupied/suitable but isn't a real
attach-capable slot.

**Fix applied (`TryEquipReplace` in `GRAD_LoadoutApply.c`):** don't trust `EquipAny`'s return value alone.
After it returns `true`, the existing diagnostic's `GetParent()` check now gates the result: if
`spawnedParent` is null (orphaned), treat it as a failure (`equipReplace[equipAnyOrphaned]` in the fail
trail), delete the orphan, and let the caller fall through to its next fallback
(`PURPOSE_ANY`/engine-chosen, then one more `TryEquipReplace` retry) instead of silently reporting success
while the character stays visually unclothed. **Not yet live-tested** — needs a Workbench restart (script
change) and a repeat of the exact repro: equip a coverall, REMOVE trousers (deletes the coverall since it
also covers LEGS), then try to re-equip separate BDU Trousers. Watch whether the fallback chain actually
lands the trousers now, or whether the log honestly reports `could not place` (still better than the
previous silent lie, but not yet a full fix if every fallback hits the same orphaning behavior).

## Recently completed, all needing a live retest together with the above

- **Headgear panel slot**: added to the right loadout panel exactly like Trousers (no storage of its own
  — worn/not-worn indicator + REMOVE button, not a fill-fraction container). `UI/Layouts/GRAD_ArsenalMenu.layout`
  gained a `HeadgearHeader`/`HeadgearBar`/`HeadgearPercent`/`ButtonRemoveHeadgear`/`HeadgearContents`
  block; `GRAD_ArsenalMenu.c` gained the matching constants, `BindUnequipButton` call, and
  `RefreshHeadgearSlot()` (mirrors `RefreshTrousersSlot()`). Reuses the existing
  `OnUnequipGarment`/`FindNamedEquippedItem` fallback added for Trousers — no new unequip logic needed.
  **Needs a layout reimport, not just a script restart.**
- **Headgear/uniform coupling bug, fixed**: headgear could previously only be swapped while a uniform was
  UNworn. Root cause: `SpawnInto`'s local AND replicated branches (`GRAD_LoadoutApply.c`) tried the
  generic `PURPOSE_ANY` insert *before* `TryEquipReplace` whenever there was no matched captured storage
  — `PURPOSE_ANY` happily stuffs the item into any free slot anywhere (a pocket) and reports success, so
  `EquipAny`'s replace-a-worn-item behavior was never reached. Fixed by trying `TryEquipReplace` first in
  that case, falling back to `PURPOSE_ANY` only if `EquipAny` itself can't place it. Also fixed a real,
  separate bug found in the same pass: the replicated branch's `ok` variable was left **uninitialized**
  when `storage` was null (undefined behavior, not a deliberate branch).
- **Baseline-cosmetic-accessory duplicate-click bug, fixed**: double-clicking an item already baked into
  a worn vest (Vest_ALICE_suspenders_1, Scabbard_Bayonet_M9, Canteen_US_01, etc.) failed with
  `preferred[ClothNodeStorageComponent] ... equipReplace[equipAnyFailed]`. Added an "already present in
  preferredStorage" short-circuit mirroring the existing captured-storage one — a redundant click on
  something already there now silently no-ops instead of warning.

## Hard constraints (unchanged)

- EnforceScript: **no ternary `?:`, no `??`** — plain if/else.
- Never `CameraManager.SetCamera(...)`. Never set `CategoryTabView`'s `SizeMode` (stays `Auto`).
- Don't read `inspiration/` (the project's own forbidden clean-room folder). A **separate, real published
  mod** (`BaconLoadoutEditor_606B100247F5C709`, found on disk this session, NOT `inspiration/`) was read
  directly this session with explicit user sign-off, on the same standard already applied to vanilla
  source: read for the pattern (what APIs are called, in what order), reimplement independently with
  verified engine calls, never copy code. Every fix landed this session was written that way — see the
  camera section above for exactly which concepts came from where.
- **Verify every native API** via `mcp__enfusion-mcp__api_search` before using it. Two fresh examples this
  session: `GenericEntity.GetWorldBounds`/`SetFixedLOD`/`SetVComponentFlags`/`GetParent` were all confirmed
  real before use; a bare `Vector(x,y,z)` global constructor was **not** found in the index and was
  avoided in favor of the already-proven string-literal + indexed-assignment vector pattern this file
  already uses everywhere.
- Full Workbench restart needed for script changes. `.layout` changes (Headgear panel) need a reimport.
- **This session's own lesson, worth restating**: when a diagnostic override is added to isolate a
  problem, revert it immediately after that one test — a flag left active silently invalidated several
  subsequent "no change" conclusions this session. If a result looks suspiciously identical to a
  completely different subject/test, check for exactly this before trusting the conclusion.
